# ADR: Auth, database access and transactional email for cloud saves

- **Date:** 2026-10-18
- **Status:** Adopt Option A incrementally; defer Option B; reject a direct session/ORM swap.
- **Scope:** Architecture decision only. No production auth, schema, email or save behavior changes in this PR.
- **Baseline:** `origin/main` at `a6c229e57d957071276bf1b99ee42e5941b8f8f9`.

## Decision

Keep **Supabase Auth + Supabase PostgreSQL** as the identity and authorization boundary. **Adopt Resend as a candidate SMTP transport for hosted magic links** once a sending domain, deliverability and operating budget are verified. **Defer Drizzle for application data** until server-owned queries actually need it; if introduced, use it first for a separate server-only feature, not as a replacement for the existing browser PostgREST/RLS save path. **Defer Better Auth** until a product requirement warrants owning session, identity and authorization infrastructure. **Reject** shipping Better Auth sessions directly against the existing `auth.uid()` policies or using a privileged Drizzle connection from the browser. This is a choice for the present app, not a claim that Better Auth cannot work with Supabase Postgres. [R1][R2][R3][R4]

No account cutover, automatic account merge, save reparenting, credential import or dual-write is approved by this ADR. The proof-of-concept and migration gates below are prerequisites for reconsidering B.

## Existing contract (observed, not hypothetical)

```text
Guest browser: game -> SaveManager -> Dexie (IndexedDB)
Signed-in browser: local save first -> SaveManager -> CloudSaveStore
                                  -> Supabase PostgREST + user JWT
                                  -> public.saves / public.profiles + RLS
Email or Google/GitHub -> Supabase Auth -> /auth/callback PKCE exchange
                      -> cookie refresh in proxy.ts -> auth store -> cloud adapter
```

- Guest play does not require auth or a server: absent env values hide account UI, while local saves live in Dexie. `src/lib/supabase/client.ts:3-12`; `src/saves/localStore.ts:85-116`; `src/saves/manager.ts:100-103`; `README.md:167-180`.
- Email uses `signInWithOtp` with a magic-link return URL; GitHub/Google use `signInWithOAuth`. The callback exchanges the PKCE code and only redirects to a local path; `proxy.ts` refreshes Supabase cookies. `src/store/useAuthStore.ts:150-183`; `app/auth/callback/route.ts:9-35`; `src/lib/supabase/callback.ts:1-37`; `proxy.ts:7-32`. Next 16 uses Proxy and App Router Route Handlers; Proxy is not an authorization boundary. [R5]
- Both title and terminal hydrate auth before selecting slots; auth events wire one cloud adapter per user and remove it on sign-out. `app/page.tsx:159-191`; `app/(game)/terminal/page.tsx:129`; `src/store/useAuthStore.ts:49-75,91-143`; `src/store/useTerminalStore.ts:203-219`.
- `CloudSaveStore` filters by `user_id` but **RLS, not that filter**, enforces ownership. Its create is insert-only; updates compare expected `revision`, and cloud payloads are migrated and validated before use. `src/saves/cloudStore.ts:25-40,56-69,71-140`; `src/saves/schema.ts:260-281`. The DB checks `unique(user_id,slot)`, row size and revision triggers. `supabase/migrations/0001_cloud_saves.sql:6-27,50-66`.
- `SaveManager` binds captures to a ready slot/engine, persists local actions immediately, delays cloud pushes, refuses lower `seq`, and treats unknown cloud revision as a conflict. Its identity/device/game checks and explicit Keep local, Use cloud, Keep both and claim flows must survive any auth change. `src/saves/manager.ts:150-211,302-337,430-465,523-542,567-642,654-790`; `src/features/auth/AuthDialogs.tsx:271-299,392-446`. `seq` is client-controlled progress, **not** proof of account ownership or leaderboard integrity. `docs/ROADMAP.md:34-35,57`.
- `public.saves.user_id` and `public.profiles.user_id` are UUID FKs to `auth.users(id) ON DELETE CASCADE`; their policies require `auth.uid() = user_id`. Authenticated role has table grants, anonymous SELECT was revoked in `0002`; SQL tests assert isolation. `supabase/migrations/0001_cloud_saves.sql:6-48,83-85`; `supabase/migrations/0002_tighten_grants.sql:1`; `supabase/tests/rls_saves.sql:1-104`. Merely adding a Drizzle schema does **not** change that execution context.
- The account dialog deletes **cloud saves**, not the auth account or local copies; it pauses in-flight writes, verifies deletions, and disables re-upload until explicitly enabled or signed out. Partial failure leaves a retry path. `src/store/useAuthStore.ts:186-266`; `src/saves/manager.ts:219-258`; `docs/PHASE0-SYNC-LIFECYCLE.md:3-13`. Full account deletion remains planned before launch in `docs/ROADMAP.md:43`.

## Alternatives and tradeoffs

| Criterion | A: Supabase Auth + Postgres + optional Drizzle + Resend | B: Better Auth + Drizzle + Resend + Supabase Postgres |
| --- | --- | --- |
| Guest-first behavior | Keep Dexie and `SaveManager`; no reason to move guest gameplay to server. | Same requirement; auth must remain optional on both routes. |
| Next integration / sessions | Existing PKCE callback, SSR cookie refresh and `getSession` hydration; server-side authorization must verify user rather than trust raw cookies. | App Router auth handler (`toNextJsHandler`), separate cookie-backed sessions, `auth.api.getSession` on server; replace Supabase callback/proxy/auth store, not just the sign-in buttons. Better Auth session cookie is opaque, not a Supabase access JWT. [R5][R6][R7] |
| Email / social / linking | Existing magic link and Google/GitHub via Supabase; Resend SMTP can deliver Supabase Auth messages. Supabase can link identities with verified matching email, but inspect its rules before any migration. [R8][R9] | Magic-link plugin + server `sendMagicLink` using Resend; social providers supported. Configure implicit linking deliberately (prefer verified explicit linking during migration); same email is not proof of same account by itself. [R10][R11] |
| Save authorization | Browser PostgREST + user JWT + grants/RLS `auth.uid()` and FK to `auth.users` remain intact. | Simplest viable route: server-only save APIs, verify Better Auth session **on every request**, scope all reads/writes to session user, preserve revision/seq/size checks and deletion pause; DB pool credentials can bypass RLS, so RLS is not a fallback. Alternate: integrate a compatible asymmetric JWT via Supabase third-party auth, change FK/ownership and RLS with issuer-aware policies, prove claim mapping end-to-end first. [R1][R2][R12] |
| Drizzle and migrations | Optional server-side ORM for new server-owned queries. Keep Supabase SQL migrations as source of truth for existing policies/triggers/grants; review generated SQL before applying. [R13] | Better Auth Drizzle PostgreSQL adapter has its own user/account/session/verification schema. Migrate with reviewed forward SQL, not `push` against live auth schema; make one system own each table. Existing `auth.users` cannot be relabelled as the Better Auth user table without a designed conversion. [R14][R13] |
| Operations / rollback | SMTP/domain setup and delivery testing; no identity split or forced sign-outs from an ORM experiment. | Own session secret, signing keys (if using JWTs), auth DB connections, provider credentials, token mail and account deletion. Reverting sign-in is not enough once IDs or writes move. [R6][R12] |

**Why B's two access paths are not interchangeable.** Supabase third-party auth accepts only suitable asymmetric OIDC JWTs with `kid` and a `role` claim; `auth.uid()` casts `sub` to UUID, and policies must handle issuer collisions. Better Auth's JWT plugin can issue JWKS-verifiable external tokens, but its normal session cookie is not that token; the JWT plugin alone is not evidence of a complete OIDC integration. A prototype must verify discovery/issuer support, accepted token shape and `auth.uid()` under the **actual** Supabase API, or use a server-only API instead. A non-UUID subject cannot satisfy the current UUID FK and policy. Do not sign Supabase-compatible tokens with a shared secret in browser code, copy a service key to the browser, or pass client-selected `user_id` through privileged SQL. [R2][R7][R12][R15]

**Cost snapshot (vendor pages checked 2026-10-18; not a quote):** Supabase Free includes 500 MB DB and 50,000 MAU; Pro starts at $25/month for one included Micro compute project, with usage-based overages. Resend transactional Free is 3,000 messages/month capped at 100/day; Pro starts at $20/month for 50,000/month. A Resend domain must be verified; custom SMTP still has Supabase Auth rate limits/configuration to validate. Supabase third-party auth may add third-party MAU billing on B's JWT route, and B adds app compute, DB connections and monitoring; moving auth does not remove the Postgres bill. Estimate actual saves (up to 2 MiB each), email sends, active users, backup retention and provider costs before a rollout. [R16][R17][R18]

## Migration contract if Option B ever clears the gate

```text
Existing Supabase user UUID --verified mapping--> new Better Auth user UUID
       |                                          |
       +-- old saves/profiles (read-only at cutover) +-- new session/owner
Guest Dexie slot --explicit review of occupied slots--> same conflict path
```

1. **Inventory and identity map.** In a restricted offline export, count `auth.users`, `auth.identities`, saves and profiles; identify unconfirmed emails, duplicated verified addresses/provider subjects, deleted-user references and slot counts. Export a one-to-one `old_supabase_uuid -> new_better_auth_uuid` mapping with a unique constraint in **both directions**. Prefer retaining the original UUID as the Better Auth user ID if the adapter, verified identity import and DB constraints all support it; otherwise allocate new UUIDs and transactionally reparent copied rows. Better Auth supports UUID IDs, but that does not create Supabase `auth.users` rows or make Better Auth sessions trusted by existing RLS. Never identify ownership from a supplied email alone. [R19] `supabase/migrations/0001_cloud_saves.sql:6-33`.
2. **Prove account control, then link.** Match existing Google/GitHub identities by provider + provider subject in restricted records only where proven; otherwise require a fresh OAuth sign-in or mailbox-control magic link and explicit account selection. For email/OAuth collisions (same verified email but different identity, changed email, missing or unverified provider email), stop auto-linking and require an authenticated, auditable manual link flow. Do not copy OAuth refresh tokens, magic-link tokens, passwords or active Supabase sessions. Mark unresolved/duplicate accounts as pending, not merged. [R8][R11]
3. **Preserve rows and conflict semantics.** Take a tested, access-controlled database backup of user/identity mappings, `public.saves`, `public.profiles` and auth metadata, plus a schema/grant/policy snapshot. On a disposable clone, copy saves with payload, slot, `seq`, revision, timestamps and `device_id` intact; check source/destination counts, per-owner slot occupancy, content hashes and orphan FK counts. Preserve `SaveGameSchema` version validation and corrupt/newer raw export. Two accounts converging on `(user_id,slot)` require an explicit user decision/export, never `ON CONFLICT DO UPDATE`. A guest's IndexedDB has no trusted owner: show both sets after sign-in and reuse claim/Keep both/Keep local/Use cloud review rather than silently uploading or wiping it. `src/saves/schema.ts:260-281`; `src/saves/manager.ts:302-337,716-790`; `src/saves/localStore.ts:118-155,195-208,296-299`.
4. **Cut over without split-brain.** Rehearse an isolated B deployment and record a short write-freeze/maintenance window or explicit owner-scoped write fence. Prefer snapshot -> verify -> flip **one writer**; do not dual-write auth or save rows across two issuers without an idempotent, replayable protocol and reconciliation. Keep old data read-only for a stated rollback window; only cut traffic once old-to-new mapping, new sign-in, session hydration and cross-device conflicts pass. Roll back routing to A **only if no B writes occurred**, or reconcile/export all B-side writes first; never delete new rows or overwrite old rows to make rollback look successful. Retire old sessions and credentials according to a documented expiry window, not an assumed instant revocation. [R20]
5. **Deletion and retention.** Decide whether “delete cloud saves,” “sign out with delete,” and “delete account” delete different scopes; do not change their meaning silently. On B, remove sessions/accounts and associated saves/profiles using tested cascades or a retryable server workflow, preserving local saves only with clear disclosure and preventing background re-upload. On A, account deletion needs a server-only admin operation, and issued JWTs can remain usable until expiry; do not promise instant revocation. Define backup retention, export/audit redaction, legal holds if applicable and purge timing with the product owner before public launch. [R21][R22] `src/store/useAuthStore.ts:186-266`; `docs/ROADMAP.md:43`.

## Proof of concept, validation and release gates

- [ ] **First gate, A:** On a disposable local/hosted test project, configure verified Resend domain and Supabase custom SMTP; test real magic-link round trip (including expiry, abuse/rate limits, bounced mail and provider-error text), Google/GitHub linking, and key isolation. Do not send production mail in the local E2E suite. [R9][R17]
- [ ] **Only if B has a product trigger:** Implement one disposable-user vertical slice on a clone: Next 16 route handler, Better Auth PostgreSQL/Drizzle adapter, Google/GitHub and magic link, a validated session, then either (a) a server-owned SaveStore API that enforces identity and conditional revision writes or (b) a proven Supabase third-party JWT flow with issuer/role/UUID and RLS assertions. Never repoint production or apply a generated schema blindly. [R5][R12][R14]
- [ ] Demonstrate two users cannot list/get/insert/update/delete each other's saves or profiles (including forged owner, anon, expired session, cross-account tabs); prove insert-only create, stale revision conflict, 2 MiB payload and 64 KiB profile limits, guest offline play, local save/backup integrity, corrupted and newer schema behavior, sign-in/claim collision and retry after network loss. The server-API variant needs explicit authorization tests even if SQL RLS tests pass. `supabase/tests/rls_saves.sql:1-104`; `src/saves/cloudStore.test.ts:35-108`; `src/saves/manager.test.ts:101-172,311-398`.
- [ ] Snapshot and restore a disposable DB; verify unique one-to-one mappings, zero unapproved merges/overwrites, FK/orphan counts, row hashes and slot occupancy; rehearse rollback after a simulated partial copy and after first B write (reconciliation required). Verify account delete, cloud-only delete and no post-delete auto-upload separately. `supabase/migrations/0001_cloud_saves.sql:6-33`; `e2e/cloud-deletion.spec.ts:29-134`.
- [ ] Preserve and extend Playwright: current **nine specs / 19 scenarios** cover local reload, direct navigation, delayed auth, Mailpit PKCE callback, bracket OCO, delayed save conflicts, conflict Keep both/Keep this device and cloud deletion on a guarded disposable Supabase stack. They do **not** establish Google/GitHub, hosted SMTP, claim upload, Use cloud, sign-out-with-delete or forced IndexedDB write failure; `docs/ROADMAP.md:45,49-59` tracks these. For B, the helper that scrapes `/auth/v1/verify`, token-delay route, DB queries joining `auth.users`, and migration-version check must be rewritten rather than interpreted as B coverage. `README.md:155-163`; `e2e/helpers/auth.ts:38-91`; `e2e/helpers/db.ts:23-37`; `e2e/global-setup.ts:4-22`; `e2e/scripts/run.sh:9-46`.

| Threat or failure | Required assertion before changing auth |
| --- | --- |
| Forged cookie, `user_id`, JWT `sub`/`role` or issuer | Verify live session/server authorization or trusted issuer and signature, then enforce per-owner read/write; anon and cross-user denied. |
| Same email on two OAuth accounts, unverified email, stolen link | Do not infer equality from email alone; verify mailbox/provider subject and explicit linking; expire/redeem links once, rate limit requests. |
| Lost update, divergent devices or mid-sync sign-out | CAS on revision, retain `seq`/device checks, generation fence, manual conflict resolution and deletion pause. |
| Partial migration, corrupted/future payload or schema drift | Snapshot, validate raw and parsed saves, compare counts/hashes and FKs, stop before flip; rehearse restore. |
| Privileged DB credential, log or backup leak | Server-only least-privilege connection, scoped queries, no key/token/raw payload logs; restrict/encrypt exports and expire them. |
| Account deletion with remaining token or local copy | Revoke/revalidate sessions, bound token TTL, no unannounced local deletion/re-upload; document backup retention. |

## Next actions

1. Keep A's current RLS contract and existing SQL migration history unchanged. Decide whether hosted mail needs Resend, then validate the SMTP/production configuration separately.
2. Finish already-tracked claim and account-deletion UX/security before public launch (`docs/ROADMAP.md:16,43,56`). Prioritize the missing auth E2E paths when touched.
3. Add Drizzle only when a concrete server-owned query needs it; treat it as a DB access tool, not an auth/session migration.
4. Reopen B only on the `AUTH-ARCH` roadmap trigger, with the POC, mapping, restore and threat matrix above as acceptance gates.
